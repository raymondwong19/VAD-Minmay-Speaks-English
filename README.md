# VAD-Minmay-Speaks-English
This project is a attempt to provide a tool that tries to replace the Minmay parts of the original Macross audio with the 2006 ADV Dub Minmay.

The first upload contains only the manually timestamped and ripped Minmay lines from intervals of 6 episodes to not be picky or selectively choose the best data! I want to test a random sample for initial training and then some more for verification. They were ripped from a dual audio ADV dub/OG audio/Commentary archive from archive.org. The WAV files are all 2/6-channel 16-bit 44.1KHz files of AC3 source, except for the english rips of episode 4 which was 2-channel 96kbps LC-AAC source because I did that earlier and had a lower quality episode sitting around. The Japanese audio are all from the same dual audio file, althrough they only had 2 channels and likewise has a 25 year difference in age from the english.
I didn't have the scripts that produced those files, but they are pretty straightforward, I simply pasted the timestamps into a LLM and asked it to generate a chain of ffmpeg commands that re-encodes the source into 16-bit s16 PCM and using -ss and -t to crop out the timestamp intervals. Episode 4 was copy pasted from GPT-5o mini, while the others are done directly locally by Qwen3-30B.
And yes, I decided to store everything in a .tar.gz archive. It did not fit through, so I went back on that.

Some cleaned audio files are made just for training, not inference. If there is background music -> BS-Roformer Resurrection as well run without any specific parameters are used for isolation. If multiple speakers need to be separated -> CREPE-MIR-1K is used simply to -> or alternatively ffmpeg is just used to cut out the offending part if it's small. Mostly for creating good enough cleaned samples, you should listen to them if you want to judge the quality in /data. The data is left as it is if it's just Minmay speaking without additional voices or minimal background audio.

I clipped more Minmay and testing directories just the normal old way as above, the same joke about gathering data before you even knew your model. However it is useful for manual Minmay Speaks English episode samples, technically.

Not much to say about the data gathering. The main thing is the logic behind using it to process clips featuring Minmay hopefully. It mostly boils down at the unrefined level to a Diarizer and a Speaker Embedding model - one can detect different speakers, and the other can identify a specific speaker by comparing cosines to references.

pyannote/speaker-diarization-community-1 is of course, a common model and was used here - the venv minmay-chroot uses Python 3.13 and was created for pyannote/speaker-diarization-community-1. The .py used for it is a mix and match of the new version of Stack Overflow everyone knows is popular nowadays. However, initially pyannote.audio==3.4.0 was installed and I had the repository mirrored locally, and even if I passed repo_type=whatever, I don't think 3.4.0 even supports running a model locally then without connecting to HF hub. However it's a new model, so after maybe two hours I just upgraded pyannote.audio to 4.0.2 and using Pipeline.from_pretrained silenced the complaint about invalid HF ids.
Torchcodec is also required, but not prebuilt for the aarch64 CPU this thing is running on. It was fairly trivial to just download the source code for 0.8.0 and build it with a contaminated ffmpeg. However 0.7.0 doesn't build with the newer arch/trixie ffmpeg and is what pyannote.audio requires, which is a lie since 0.8.0 seems to work fine.

Multiple Embedding models are tried, most of them are well, old (4-5 years old), and therefore depended on old versions of libraries. The lack of HF spaces using those models meant that references are unreliable and scare. First I tried SpeechBrain's ECAPA Voxcelel with the latest python 3.13 and torch. However no matter what I did, I could never get the model to accept any waveform. That took over 4 hours of confusion.
So I switched to pyannote/embedding, but that likewise took several hours of testing, never getting to passing the data to it, but because it's a older model that does not work with pyannote.audio==4.0.2 and there is no way to resolve the repo_type problem. I built Python 3.10.13 in a new chroot for it too. And at one point I even had a unlearnt MFCC fallback which didn't have very good performance, because well, we want to use a model that has learnt how speech works.

So eventually I just pulled a simpler ONNX pretrained version of WeSpeak from Hugging Face and reused the Python 3.10.13 venv - named minmay-embedder. That was rather quick, ONNX didn't complain about repository ids, but did give me the usual complaint about the input dimensions being not what it would try to process. I WAS ABLE TO FIZZ IT rather easily and had the LLM generate a block that uses librosa to fit the inputs to generate a cache npz of the reference data (all EN files dumped into a new dir called enroll-en). Librosa didn't do anything for some reason and forced a switch to Scipy and soundfile. That got the npz done.

And so a new script was written that takes the npz from data/enroll-en and compares it to a embedding of whatever directory is pointed to determine the certainty of which speaker is Minmay in the timestamps given by the diarizer. Working in conjuction with a bash script that uses jq and ffmpeg to save all the speaker IDs from the diarizer and their times into separate directories in which the master script runs the voiceprinter over all dirs named speaker##.

Well it took a long time, but eventually all it takes is to isolate the JSON timestamps of the speaker with the highest average score, and then save another JSON with all the time in the target audio file that is not the speaker's time to talk. That NOT time will be snipped out from the japanese audio named japanese.wav, and the speaker time will be snipped from the dub audio named dub.wav, saved in order as 1.wav 2.wav 3.wav ... and then concat'ed into a output.mp3 in the temporary working directory.

And that's it for V1. It does something at least. I did wipe the venvs and the pyannote dir since I don't think I am allowed to distribute them and they're huge, so you recreate them.
